# F5 役割・判断UXの試作記録（2026-11-02）

## 採用

- 導入・練習に「市長＝プレイヤー」「住民＝困りごとを伝える生活者」「まちづくり支援AI＝選定を委任できる相手」を短い役割カードで表示。判断画面では住民の声と支援AIを別ラベルにし、既存4キャラクターは案内役として維持。
- ソロ初回の診療所分岐は現状を保護。ソロ2～4回目に人を選んだ場合のみ、2つの演出上の検討方針を表示する。どちらも同じ `human` 判断・同じ施策・同じスコアで、選択した方針だけをタブ内メモへ残す。再読み込みで失われ、実際に行動した証拠とは扱わない。
- 支援AIは既存の `ai` 選択ですぐ委任できる。速度と見える成果の利点、個別事情の重み付けを把握しにくい点を選択後に短く説明。街の相談・依頼が重なる状況は「展示上の情景」と示し、架空件数・締切・待ち時間を設けない。
- 会見はソロのブラウザ内方針メモがある場合に限り選択内容を反映。D1/API/engineには保存しない。

## 非採用・影響

- 共有の3択化、投票集計・API・D1の変更、具体策別スコア、実行した行動の記録は採用しない。共有は従来の `human` / `ai` 二値票のまま。
- エンジン、初回診療所、ソロ4判断、共有7判断・23秒、6結末、会見構造、Canvas、マニフェストは変更しない。
- 表示追加による画面密度と理解度は試遊で確認が必要。小画面の横スクロール、操作領域、フォーカスは実機確認が必要。

## 要確認・試遊ポイント

- 初見で3役割を区別し、住民と支援AIを同一人物と誤認しないか。
- 人の2方針が「演出上の検討」で同一結果と理解され、行動記録や正解扱いに見えないか。
- AIの即時性・利益と、選定根拠の把握範囲の違いが公平に伝わるか。人を選ぶことが正解に見えないか。
- 依頼の重なりがタイマーや圧力に見えず、タップまたはスキップを妨げないか。
- 会見の個人方針が共有参加者の投票・承認と混同されないか。再読み込み時の記録消失表示が十分か。
- 390×844、1024×768、1920×1080で表示・タップ・フォーカス・reduced-motionを実機確認する。


## 実装後の検証結果（親エージェント）

- 接続Macの通常環境で npm test 80/80件成功（失敗0・スキップ0）。Worker／単体HTMLビルド、成果物検証 node scripts/validate-artifact.mjs に成功。
- Playwright Chromiumのソロ390×844で、イントロ→3役割の表示→チュートリアル→診療所のAI提案承認→住民の質問と通院支援→第2判断の人側2方針選択→第3判断への進行を実操作。人方針は同一エンジン選択の説明であることを表示。
- 390×844、1024×768、1920×1080のソロ画面で document.documentElement.scrollWidth===clientWidth を確認。共有モニター画面も1920×1080、1024×768で横スクロールなし・QR画像生成を確認。
